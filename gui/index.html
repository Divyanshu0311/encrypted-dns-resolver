Tests

Lookup

Resolves one name and shows its addresses, how long it took and where the answer came from. Ask the same name twice: the first answer comes from an upstream (milliseconds), the second from our cache (well under a millisecond). This server goes through the whole middleware, exactly like a DNS-over-TLS query; the other choices ask one resolver directly.

Compare resolvers

Asks every resolver the same name twice, starting from empty caches.
  • Forwarding asks a big public resolver, which usually has the name cached already: fast.
  • Recursive walks root → TLD → the domain's own servers itself: slowest when cold, but trusts no one else.
  • The second ask comes from our cache: near zero for everyone.

Continuous traffic

A steady stream of queries from 1000 simulated clients that keeps going until you press Stop, the way a real network uses its resolver. Every panel on the right comes alive. While it runs, switch the resolver at the top, inject failures, or start an Abuse test on top of it.

Load test

Sends a fixed number of queries as fast as possible and measures throughput and latency: a benchmark. Identical names arriving together are resolved once (coalesced), and repeats are answered from the cache.

Abuse protection

One client sends queries continuously at a fixed rate.
  • Under its limit it is served normally and never blocked: heavy is not abusive.
  • Over its limit the excess is refused (rate limited). Enough refusals in a short window and the client is blocked: every query refused, DNS-over-TLS connections dropped before the TLS handshake.
  • Other clients carry on unaffected the whole time.

Failures and circuit breakers

Makes a share of lookups fail inside the workers, as if the upstream were broken.
  • After 3 failures in a row a worker's breaker opens: it stops taking work, so clients get a quick SERVFAIL instead of waiting.
  • After a cooldown it goes half-open and lets one probe query through. Success closes it again.
Watch Circuit breakers on the right. It needs traffic, so press Send traffic first.

Upstream certificates

Opens a TLS connection to an upstream exactly as the server does before using a DNS-over-TLS upstream, and shows the certificate it presented.
  • The chain must lead to a trusted CA (the system's, or upstream_ca_file).
  • The certificate must be issued to the name after # in the config or, without one, list the IP address.
  • It must be within its validity dates.
When a check fails the question is never sent, and the query gets SERVFAIL. It never falls back to plain DNS. Try the impostor: Cloudflare's address claiming to be Google.
